- 14:16 Score components are stored already weighted (upstream <= 0.40 etc.), so `score = sum(components) * penalty` and the UI can draw stacked bars directly.
- 14:16 Exact formulas used for fixtures (Lane B implements the same): upstream = anomalous services that transitively call it / (anomalous count - 1); precedence = share of its anomalous transitive callers whose onset is later than its own (0 if it has none); change = 1 if a change event on it within 10 min before onset; severity = its peak z / max peak z in the incident.
- 14:16 `alert_count` = number of `kind == "alert"` events grouped into the incident. The hero fixture has 14 alerts, so the headline reads "14 alerts, 1 cause".
- 14:16 Timestamps are real UTC with a trailing Z. 14:02 IST is stored as 08:32Z and the UI renders in IST. The CLAUDE.md example `14:02:11Z` was illustrative.

The ambiguous fixture yields ledger-svc 0.433 vs postgres 0.430 (ABSTAINED: margin 0.003, top score < 0.45).

- 14:26 [Lane A] The simulator is one class (`Simulator.advance(until)`) that generates every event with ts < until without sleeping. The offline `simulate(seconds, faults, start, seed)` and the live loop both drive it, so tests and the demo share one code path.
- 14:27 [Lane A] Fault propagation walks CALLERS from the root, but only into the services listed in that fault's degraded-metrics table. This keeps redis_down off payments/ledger/postgres by construction, not by luck.
- 14:28 [Lane A] Alert lag is per role: gateway 0.3 to 0.9 s after its onset, root 4 to 8 s, others 2 to 5 s. The gateway pages first in most seeds and the root pages late, so alert order is not causal order.
- 14:29 [Lane A] Starting the live sim backfills 60 s of healthy baseline instantly, so the engine has a baseline before the first fault. Injecting a fault while stopped starts the sim. Injecting a fault that is already active is ignored.
- 14:30 [Lane A] Reset clears faults, events and incidents but keeps a running sim running on a fresh baseline. Sim event ids never restart, so the UI cannot confuse an old evt id with a new one.
- 14:31 [Lane A] Store calls analyze in a worker thread (`asyncio.to_thread`) at most once per second from the background loop, and guards against a reset that happens mid-analyze. Any analyze exception keeps the previous incidents and is logged once per distinct error.
- 14:31 [Lane A] Age eviction (15 min behind the newest event) only drops sim events, so an uploaded log with old timestamps is not evicted at once. The 50k count cap applies to everything.
- 14:32 [Lane A] SSE: events are dumped with exclude_none (matches the fixture, which omits null value/message), incidents and topology_state keep nulls (also matches). sse-starlette is told sep="\n" because its default is CRLF. On connect a client first receives the current topology_state and every known incident.
- 14:33 [Lane A] SSE `event` messages are capped at 20 per wall-clock second, picked by priority alert > change > non-info > info, then sent in ts order.
- 14:34 [Lane A] `/api/stream?limit=N` closes the stream after N messages. Used by tests and curl; the UI omits it.
- 14:34 [Lane A] Uploaded events get ids `evt_upNNNNNN` from the store, so they never collide with sim ids `evt_NNNNNN`. Upload timestamps are normalised to UTC with ms and Z; naive timestamps are read as UTC.
- 14:35 [Lane A] Live sim autostart on boot is opt-in via env `SIM_AUTOSTART=1` (default off), so tests and a cold Render boot stay quiet until the UI presses start.
- 14:41 [Lane B] Incident id = `inc_` + first 10 hex of sha1("<opening service>|<opened_at>"), where the opening service is the earliest-onset service. It does not depend on how many incidents came before, so it stays the same as the store re-runs analyze on a growing (or sliding) event list. Checked on Lane A's real simulator: one id per fault from first detection to the end.
- 14:41 [Lane B] Metric baseline is an EWMA mean and variance per (service, metric) with alpha = max(0.1, 1/(n+1)), so the first samples act as a plain mean. std floor = max(std, 10% of |mean|, per-unit eps: 1 for _ms and _pct, 0.01 for rates). Samples with z >= 3 never update the baseline, so a sustained fault cannot poison it.
- 14:41 [Lane B] A metric sample is anomalous at z >= 4 only when its neighbour sample is also >= 4 (or z >= 10 on its own). One noisy scrape never pages, and the onset is still the first sample of the run.
- 14:41 [Lane B] Error logs and failed requests are weak signals: they count as a burst (2+ error logs in 10 s, or 3+ failed requests in +-10 s that are at least 20% of that service's traffic) or when a strong signal (metric, alert, critical log) on the same service is within 5 s. That lets the first error log set the onset, as in the fixtures. An episode with no strong signal needs 3+ points, so two stray error logs never open an incident.
- 14:41 [Lane B] A service that stops reporting metrics (gap > 3 x its median scrape interval and > 6 s, judged against the latest event ts) is anomalous with signature dependency_down. Its evidence is its last scrape. This covers a redis that dies silently instead of reporting error_rate 1.0.
- 14:41 [Lane B] Anomalies are kept as per-service episodes split by 60 s quiet gaps, not one onset per service forever, so a second fault on the same service later in a session opens a new incident.
- 14:41 [Lane B] Single-service incident: the upstream share is 0/0 in the 14:16 formula. We define it as vacuously 1.0 (nothing contradicts it), so a lone bad deploy scores 0.4 + 0.2 + 0.1 = 0.7 and opens instead of always abstaining. Precedence stays 0 (rule says 0 when it has no dependents).
- 14:41 [Lane B] Signature rules, in order: connection_pool_exhausted (db_pool_in_use_pct >= 95, or connection-slot logs or a pool alert), error_spike_after_deploy (change component > 0), dependency_down (silence, error_rate >= 0.9, or connection refused / unreachable logs), then error_spike if an anomalous error_rate peaks at >= 0.25, else latency_spike if a latency metric is anomalous, else error_spike. This gives psp_slow "latency_spike" even though the PSP also times out some calls.
- 14:41 [Lane B] Abstain margin is compared after rounding to 3 dp, so 0.600 - 0.450 counts as 0.150 and does not abstain on float noise.
- 14:41 [Lane B] A single-service incident younger than 3 s (vs latest event ts) is held back. On the real simulator the gateway pages about 0.5 s after its onset, before the services between it and postgres are confirmed, which produced a ghost "api-gateway" incident for one recompute.
- 14:41 [Lane B] Grouping links episodes only when onsets are within 5 min (spec literal). An earlier draft also linked any onset inside a long running episode, which would swallow a second fault (psp_slow injected minutes after db_pool) into the first incident.
- 14:41 [Lane B] Timeline adds one entry per change event that produced a change component (caused_by null), so the red herring deploy is visible in the story even though it is not blamed. Recommendations add "do not roll back the victims" and, for a non-root service with a change, "keep that change in place: it is not the cause".
